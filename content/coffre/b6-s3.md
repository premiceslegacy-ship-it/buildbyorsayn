## Un seul gros prompt finit par mélanger les métiers

Il choisit la marque, dessine le formulaire, écrit la base et valide la sécurité. Personne ne sait ensuite quelle règle a décidé quoi.

Un bon système garde une direction commune et appelle le bon savoir-faire au bon moment.

## Tu vas répartir sans perdre la cohérence

Un sous-skill apporte une méthode spécialisée. Il ne reçoit aucun accès supplémentaire et ne décide pas du projet entier.

À la fin, tu auras relié une décision visuelle et une décision backend par un accord commun.

## Le projet garde la vue complète

ORACLE by Orsayn tient le besoin, les décisions et l'ordre du projet. Le sous-skill visuel traite ce que la personne voit. Le sous-skill backend traite ce qui protège et fait circuler les données.

[[schema:QuiFaitQuoiProduit]]

Le responsable d'intégration relit l'ensemble. Il peut accepter une sortie, demander une correction ou arrêter le passage suivant.

Pourquoi ? Parce qu'un expert peut très bien réussir sa partie et casser une dépendance ailleurs.

==Le spécialiste approfondit une décision. Il ne remplace pas la direction du projet.==

## Le même écran demande plusieurs métiers

Regarde un formulaire de création de compte. Le visuel choisit l'ordre, les libellés et les messages d'erreur. Le backend vérifie les données et les droits.

[[maquette:FormulaireDeuxMetiers]]

Le domaine `ux-ui-design` prépare l'expérience, la marque et le copy d'interface. Il montre aussi les états utiles sur mobile.

Le domaine `backend-orsayn` prépare les données, les comptes, les routes, les webhooks et les accès. Un webhook est un message automatique envoyé par un service.

Concrètement, les deux domaines partagent le contrat des rôles avant de travailler. Ils ne devinent pas chacun leur propre liste.

:::retiens
Une dépendance commune se décide une fois, puis chaque spécialiste travaille sur cette version.
:::

## La délégation revient toujours au produit

Le projet formule la décision. Le spécialiste remet son travail et ses contrôles. L'intégrateur cherche les contradictions. Le projet accepte ou corrige.

[[schema:BoucleDelegation]]

La version retenue reste notée avec sa raison. La prochaine personne sait donc ce qui remplace l'ancienne décision.

Pense à un chantier. Le plombier et l'électricien ont leur métier. Le plan commun évite pourtant de placer une prise derrière une arrivée d'eau.

## Choisis le plus petit mode de travail suffisant

Une tâche simple reste directe. Une méthode spécialisée appelle un skill. Un travail ouvert peut demander une délégation séparée.

[[schema:ChoisirDirectSkillOuDelegation]]

Pose trois questions. Le travail demande-t-il une expertise différente ? Les données ou les risques changent-ils ? Les sous-tâches peuvent-elles avancer sans se gêner ?

Multiplier les agents ajoute des transmissions et des contradictions. Cela ne rend pas automatiquement le résultat meilleur.

==Une délégation se justifie par le travail, jamais par l'envie d'afficher une équipe d'agents.==

## Vérifie les rôles sur le vrai écran

Une liste de permissions semble souvent correcte dans un document. Le test doit montrer ce que chaque rôle voit et peut faire.

[[maquette:RevueDesRoles]]

Le compte membre voit son dossier. Le responsable voit les dossiers de son équipe. L'administrateur peut gérer les accès. Chaque refus est testé aussi sérieusement que chaque autorisation.

## Prends Julie, responsable d'un cabinet de kiné

:::exemple Julie fixe les rôles avant le formulaire
Julie veut permettre aux patients de demander un rendez-vous. Le designer prépare un choix de praticien et un champ de motif.

Le développeur découvre ensuite que l'accueil peut voir les horaires, mais pas les notes médicales. Le praticien doit voir ses propres rendez-vous seulement.

Julie valide d'abord les trois rôles. Le formulaire affiche alors les bons champs et le backend applique les mêmes règles.

L'équipe teste ensuite chaque compte. Le design et la protection des données racontent enfin la même chose.
:::

## À toi de jouer

Compte trente minutes aujourd'hui.

1. Choisis un écran important de ton projet.
2. Écris la décision visuelle qu'il demande.
3. Écris la décision backend qui lui répond.
4. Nomme l'accord que les deux doivent partager.

À la fin, tu as deux décisions et un contrat commun.

## Version pour ton IA

```text
Analyse cette tâche et choisis le mode de travail le plus simple.

Choix possibles :
1. exécution directe ;
2. skill spécialisé ;
3. travail séparé confié à un spécialiste.

Justifie le choix avec :
- la difficulté ;
- les données utilisées ;
- le risque ;
- les dépendances ;
- le contrôle final.

Si tu proposes une délégation, écris :
- l'objectif ;
- les sources ;
- ce qui est interdit ;
- le résultat attendu ;
- la personne qui réunira le travail.

N'accorde aucun accès supplémentaire.
```
